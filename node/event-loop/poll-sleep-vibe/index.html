Node event loop

I Have No Eyes and I Must Sleep

Why your "idle" Node process is actually doing burpees.

Core message: the poll phase is designed to wait. If a Node process burns a full core while "idle," your app is preventing poll from blocking.

Poll is where Node sleeps

Node runs your JavaScript on one main thread. It delegates I/O waiting to libuv, which uses the OS to block in epoll_wait (Linux), kqueue (macOS/BSD), or IOCP (Windows). That waiting happens in the poll phase. In a healthy idle process, poll blocks and the CPU sleeps.

If you schedule immediate work (like setImmediate or a tight microtask loop), the poll phase gets a timeout of 0. That means it returns immediately, the loop spins, and you burn a core while doing almost no useful work.

Vocabulary: blocking means the thread is asleep in the kernel, waiting for I/O; poll phase is where libuv waits; wakeup storm is a loop of fast wakeups because a file descriptor stays "ready"; microtasks are Promise/nextTick callbacks run before the loop can advance; starvation is when those microtasks keep the loop from reaching timers or I/O.
Deep dive: why poll blocks (conceptually)

libuv computes the next timer deadline and asks the kernel to block until either I/O becomes ready or the timeout expires. If there is immediate work (like setImmediate callbacks), it sets the timeout to 0, which tells the kernel to return immediately. That is the root of many "idle but hot" Node processes.

Four demos: sleep, spin, starve, storm

Each demo is a self-contained Node script. Run them locally on Linux for the best observability. macOS has dtruss and ktrace instead of strace, and Windows uses ETW or Windows Performance Recorder. The concepts still apply, but the commands below are Linux-first.

Safety: Do not run strace or perf in production without permission. These tools can be invasive and may reveal sensitive data.

Demo 1: True idle sleep (poll blocks)

demo: idle-sleep.js

Summary: A TCP server with no activity. The process stays alive but the poll phase blocks in epoll_wait. CPU should remain near zero.

Run it

node demos/idle-sleep.js

File: demos/idle-sleep.js

const net = require('net'); const server = net.createServer((socket) => { socket.end('hello\n'); }); server.listen(3333, '127.0.0.1', () => { console.log('idle-sleep: listening on 127.0.0.1:3333'); console.log('pid:', process.pid); console.log('Try: nc 127.0.0.1 3333'); });
What you should observe:
  • CPU stays near 0% while idle.
  • epoll_wait blocks for long durations.
  • Connecting with nc wakes the loop briefly.
How to detect this:
ps -eo pid,comm,args,%cpu --sort=-%cpu | head
sudo strace -tt -p PID -e trace=epoll_wait,ppoll,poll,select,nanosleep,clock_nanosleep

Expected pattern: epoll_wait blocks and returns infrequently.

sudo perf top -p PID

Expected pattern: low overall samples, occasional epoll_wait or uv__io_poll.

sudo perf record -F 99 -p PID --call-graph dwarf -- sleep 10
sudo perf report
Node profiling options
node --cpu-prof demos/idle-sleep.js

--cpu-prof writes a .cpuprofile file you can open in Chrome DevTools (Performance tab). For the idle case, the profile should be mostly empty.

node --prof demos/idle-sleep.js
node --prof-process v8.log

--prof writes v8.log. Process it with node --prof-process v8.log to see where time was spent.

Fix patterns:
  • None needed. This is the healthy baseline: poll sleeps.

Demo 2: setImmediate spin

demo: setimmediate-spin.js

Summary: A recursive setImmediate loop. Poll always has immediate work, so it never blocks. One core pegs at 100%.

Run it

node demos/setimmediate-spin.js

File: demos/setimmediate-spin.js

let iterations = 0; const started = Date.now(); function spin() { iterations++; setImmediate(spin); } spin(); setInterval(() => { const elapsed = (Date.now() - started) / 1000; const perSec = Math.round(iterations / elapsed); console.log('setImmediate spin:', perSec, 'iterations/sec'); }, 1000);
What you should observe:
  • CPU ~100% of one core.
  • Very high iterations/sec.
  • Almost no time spent sleeping in poll.
How to detect this:
ps -eo pid,comm,args,%cpu --sort=-%cpu | head
sudo strace -tt -p PID -e trace=epoll_wait,ppoll,poll,select,nanosleep,clock_nanosleep

Expected pattern: rapid epoll_wait calls returning immediately (timeout 0). This is a classic spin.

sudo perf top -p PID

Expected pattern: lots of userland JS/V8 frames; little kernel blocking.

sudo perf record -F 99 -p PID --call-graph dwarf -- sleep 10
sudo perf report
Node profiling options
node --cpu-prof demos/setimmediate-spin.js

Open the .cpuprofile in Chrome DevTools. You should see heavy time in JS and V8 internals.

node --prof demos/setimmediate-spin.js
node --prof-process v8.log

Process v8.log with node --prof-process v8.log to get a summary.

Fix patterns:
  • Batch work and yield with timers when possible.
  • Use setImmediate sparingly; avoid infinite immediate loops.
  • Prefer event-driven I/O or backpressure rather than scheduled spin.

Demo 3: Microtask starvation

demo: microtask-starvation.js

Summary: A never-ending microtask chain (Promise or process.nextTick) prevents the loop from reaching timers or I/O. The poll phase rarely gets a chance to block.

Run it

MODE=promise node demos/microtask-starvation.js
MODE=nextTick node demos/microtask-starvation.js

File: demos/microtask-starvation.js

const mode = process.env.MODE || 'promise'; const yieldEvery = Number(process.env.YIELD_EVERY || 0); let iterations = 0; const started = Date.now(); let timerFires = 0; let lastTimer = Date.now(); setInterval(() => { const now = Date.now(); const drift = now - lastTimer - 1000; lastTimer = now; timerFires++; console.log('timer fired', timerFires, 'drift(ms)=', drift); }, 1000); function schedule() { iterations++; if (iterations % 5_000_000 === 0) { const elapsed = ((Date.now() - started) / 1000).toFixed(1); console.log('microtasks:', iterations, 'elapsed(s)=', elapsed); } if (yieldEvery > 0 && iterations % yieldEvery === 0) { setImmediate(schedule); return; } if (mode === 'nextTick') { process.nextTick(schedule); } else { Promise.resolve().then(schedule); } } console.log('mode:', mode, 'yieldEvery:', yieldEvery || 'none'); console.log('pid:', process.pid); console.log('Try: YIELD_EVERY=100000 MODE=promise node demos/microtask-starvation.js'); schedule();
What you should observe:
  • CPU high even though no useful work is done.
  • Timers are delayed or never fire (starvation).
  • nextTick is usually more aggressive than Promise microtasks.
How to detect this:
ps -eo pid,comm,args,%cpu --sort=-%cpu | head
sudo strace -tt -p PID -e trace=epoll_wait,ppoll,poll,select,nanosleep,clock_nanosleep

Expected pattern: fewer epoll_wait calls; the process burns CPU in userland.

sudo perf top -p PID

Expected pattern: heavy JS/V8 time, little kernel wait.

sudo perf record -F 99 -p PID --call-graph dwarf -- sleep 10
sudo perf report
Node profiling options
node --cpu-prof demos/microtask-starvation.js

Expect hot stacks dominated by Promise/nextTick processing.

node --prof demos/microtask-starvation.js
node --prof-process v8.log
Fix patterns:
  • Avoid unbounded microtask chains; insert a yield (timer or immediate) after N iterations.
  • Prefer Promise chains that naturally resolve, not self-scheduling microtasks.
  • Move heavy loops to worker threads when possible.

Demo 4: Wakeup storm

demo: wakeup-storm.js

Summary: A local client sends tiny chunks continuously. The server socket is always readable, so epoll_wait returns immediately over and over. This creates a wakeup storm.

Run it

node demos/wakeup-storm.js
FIX=1 node demos/wakeup-storm.js

File: demos/wakeup-storm.js

const net = require('net'); const forever = process.argv.includes('--forever'); const fix = process.env.FIX === '1'; const durationMs = 10_000; let bytes = 0; let events = 0; let start = Date.now(); const server = net.createServer((socket) => { socket.on('data', (chunk) => { bytes += chunk.length; events++; if (fix) { socket.pause(); setTimeout(() => socket.resume(), 10); } }); }); server.listen(0, '127.0.0.1', () => { const port = server.address().port; console.log('wakeup-storm server on port', port, 'fix:', fix); console.log('pid:', process.pid); startClient(port); }); function startClient(port) { const client = net.connect(port, '127.0.0.1'); client.setNoDelay(true); const payload = Buffer.alloc(512, 0x61); function writeLoop() { let ok = true; while (ok) { ok = client.write(payload); } if (!ok) { client.once('drain', writeLoop); } } client.on('connect', () => { writeLoop(); }); } setInterval(() => { const now = Date.now(); const sec = (now - start) / 1000; const eps = Math.round(events / sec); const bps = Math.round(bytes / sec); console.log('events/sec', eps, 'bytes/sec', bps); if (!forever && now - start > durationMs) { console.log('stopping after', durationMs / 1000, 'seconds'); process.exit(0); } }, 1000);
What you should observe:
  • CPU stays high due to constant readiness events.
  • High events/sec even though the handler does little work.
  • With FIX=1, events/sec drops and CPU improves.
How to detect this:
ps -eo pid,comm,args,%cpu --sort=-%cpu | head
sudo strace -tt -p PID -e trace=epoll_wait,ppoll,poll,select,nanosleep,clock_nanosleep

Expected pattern: rapid epoll_wait wakeups because the socket is always readable.

sudo perf top -p PID

Expected pattern: uv__io_poll and JS callbacks show up frequently.

sudo perf record -F 99 -p PID --call-graph dwarf -- sleep 10
sudo perf report
Node profiling options
node --cpu-prof demos/wakeup-storm.js
node --prof demos/wakeup-storm.js
node --prof-process v8.log
Fix patterns:
  • Respect backpressure: pause reads and resume after processing batches.
  • Aggregate or batch small writes to reduce wakeups.
  • Use flow control on streams (pause/resume or highWaterMark tuning).

How to catch the problem in the wild

This is a quick workflow for Linux. Always get permission before tracing production workloads.

ps -eo pid,comm,args,%cpu --sort=-%cpu | head
sudo strace -tt -p PID -e trace=epoll_wait,ppoll,poll,select,nanosleep,clock_nanosleep
sudo perf record -F 99 -p PID --call-graph dwarf -- sleep 10
sudo perf report
node --cpu-prof your-script.js
node --prof your-script.js
node --prof-process v8.log

Open .cpuprofile in Chrome DevTools (Performance tab). For --prof, run node --prof-process v8.log for a text summary. Tools like 0x or clinic flame can help, but they are optional.

Expected perf/strace patterns (likely, not guaranteed)
  • Idle sleep: long epoll_wait blocks, few samples.
  • Spin: epoll_wait returns immediately, high userland CPU.
  • Microtask starvation: scarce poll syscalls, heavy JS/V8 time.
  • Wakeup storm: frequent epoll_wait returns due to always-ready fd.

Exact symbol names vary by Node version and build flags. Look for patterns, not perfect matches.

Expected flamegraph sketches (ASCII)

Idle (sleeping) | epoll_wait ....................... | Spin (setImmediate) | JS (setImmediate) | v8:: | JS | v8:: | JS | v8:: | Microtask starvation | JS microtasks | v8::Promise | JS microtasks | v8::nextTick | Wakeup storm | uv__io_poll | on('data') | uv__io_poll | on('data') | ... |

Checklist: if you see 100% CPU while "idle"

  • Confirm the poll phase is not sleeping (strace shows epoll_wait returning immediately).
  • Look for self-scheduling immediates or microtask chains.
  • Check for always-ready sockets (wakeup storm), especially small writes.
  • Use Node CPU profiles to find hot JS stacks.
  • Remember: poll sleeping is good. Spinning is bad.

Conceptual caveats

The event loop has more phases (timers, pending, idle/prepare, poll, check, close). The diagrams and simulator are a teaching aid. Internal details evolve across Node versions. The important invariant remains: poll is where the thread blocks. If your process is burning CPU while "idle," it is almost always because something keeps the poll phase from sleeping.
